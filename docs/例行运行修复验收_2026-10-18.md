## 二、逐条根因与验证

### B1 子进程未注入 PYTHONPATH —— 这是"每天重启几百次"的真凶

**症状**：看板所有 `/api/live/*` 返回 500，健康检查永远失败，watchdog 每 30 秒重启一次服务。日志里 10-15 当天有 15:00 / 15:02 / 15:05 / 15:26 / 17:40 多次"拉起 deck_server"。

**根因**：`python deck/deck_server.py` 启动时 `sys.path[0]` 是 `deck/` 目录，不是项目根。`deck_server.py` 里 `from data.io_utils import ...` 找不到 `data` 包 → 进程启动即崩。

**修复**：`clean_env()` 显式把项目根注入 `PYTHONPATH`：

```python
_pp = env.get("PYTHONPATH", "")
env["PYTHONPATH"] = str(BASE) + (os.pathsep + _pp if _pp else "")
```

**验证**：
```
$ curl --noproxy '*' -o /dev/null -w "%{http_code} %{time_total}s" http://127.0.0.1:8787/api/live/opp
200 0.039s
```
修复前该接口 100% 返回 500。

### B2 `os.kill(pid, 0)` 在 Windows 上是杀进程，不是探测

**症状**：守护偶发退出后不再自愈。

**根因**：POSIX 下 `os.kill(pid, 0)` 是"存在性探测"（0 号信号无副作用）。**Windows 上没有信号语义**，CPython 把它实现为 `TerminateProcess(pid, 0)` —— 传 0 等于**无条件终止该 pid**。后果：
- pid 被系统复用（重启后极易发生）时，会误杀一个无辜进程；
- 杀完返回成功 → 误判"守护还活着" → 本实例直接退出 → 看板再也起不来。

**修复**：改为只查询、零副作用的两条路径——psutil 读命令行确认确为 `watchdog.py`；无 psutil 时用 `OpenProcess` + `GetExitCodeProcess`。`os.kill` 仅在 POSIX 分支保留。

**验证**：`--status` 多次调用后无进程被杀（修复前会杀掉 pid 文件里的进程）。

### B4 虚假绿灯：任务查不到时默认"启用中"

**症状**：`python dev_auto.py --status` 一直显示 `计划任务: 🟢 启用中（LWQuant-DevDriver）`，而该任务**根本不存在**。

**根因**（两层）：
1. `TASK_NAME = "LWQuant-DevDriver"` 是历史前缀，实际注册名是 `DSHQuant-DevDriver`，两套名字互不相认；
2. `except Exception: return True` —— 查询失败（任务不存在必然失败）被当成"启用"。

这是比红灯更危险的失败模式：**红灯会让人去修，绿灯让人以为没事**。

**修复**：
- 新增 `data/task_registry.py` 作为任务名唯一事实源：按 `-后缀` 解析，前缀无关（`DSHQuant-*` / `LWQuant-*` / 将来改名都能命中）；
- `_task_enabled()` 改为三态 `True / False / None`，`None` 表示"任务不存在或查询失败"，**不再用 True 兜底**；
- `--status` 按三态显示：`🟢 启用中（DSHQuant-DevDriver）` / `🔴 已禁用` / `⚪ 未注册（例行运行不会自动触发）`。

**验证**（四种情形逐一实测）：
```
已注册  DevDriver      -> DSHQuant-DevDriver  Ready   True
不存在  FactorDaily    -> None                Missing False
不存在  NoSuchTask123  -> None                Missing False
查询失败               -> Unknown             None
查询失败 snapshot.ok   -> False  queryable=False
```

### B5 健康检查对着错误的规格报红灯

**根因**：`health_scan.py` 硬编码 7 个 `LWQuant-*` 任务名，其中 `FactorDaily` / `FactorArchive` 对应的 `data/factorpool/core/scheduler.py` **在本构建中根本不存在**（因子池是外包组件，未随包发布）。结果是调度维度永远红灯，且红灯的原因指向"任务缺失"而非"规格错误"。

**修复**：改走 `task_registry.snapshot()`；并把不存在的规格从清单中移除——不对着不存在的规格报红灯。

**验证**：6/6 就绪，`sched.ok=True`。

### B6 看板页面任务名与状态失真

**修复**：

- 下次运行时间改走 `task_registry.query_next_runs()`（PowerShell `Get-ScheduledTaskInfo`，一次调用拿全部任务，不受黑名单影响）；

### B7 管道锁泄漏：周末跑一次，后面 2 小时全被跳过

**症状**：`data/logs/daily_pipeline.lock` 在 16:02:53 被写入后一直残留。

**根因**：锁只在 `main()` 正常结束时 `unlink`。而"周末跳过"和"异常退出"两条路径都直接 `return`，锁文件留着。锁的过期判定是 2 小时，于是 2 小时内的任何运行都会打印"另一管道正在运行中 → 本轮跳过"——**静默不干活**。

**修复**：锁的获取与释放拆开，`main()` 用 `try/finally` 统一释放；写锁失败时"无锁运行但不持有锁"，避免结束时误删别人的锁。

**验证**：本次 16:02 那次残留锁已由新逻辑覆盖；周末/异常路径不再留锁。

### B8/B9 政策面静默降级，且原因被截断

**症状**：`timing_system.py` 日志出现 `[policy_hook] 计算失败: unable to open database file`，但择时仍输出"政策 50（中性）"。

2. 真正缺失的是 `data/cache/policy/epu.db`——整个 policy 目录不存在，sqlite 只报"unable to open database file"，而 `policy_hook` 又把异常截断到 60 字符，看不到缺哪个库。

**修复**：
- `MACRO_DB` / `BARS_DB` 改 `BASE` 绝对路径；
- `load_panel()` 在连接前显式检查两个库是否存在，缺哪个报哪个；
- `policy_hook` 打印完整原因，并把失败结果缓存 12h（缺库是结构性缺失，重试无意义且刷屏）。

**验证**：

### B10 两个 deck_server 同时占 8787，请求随机落在新旧代码上

**症状**：同一个 `/api/system_live` 响应里，`scheduled` 用斜杠日期格式（旧 schtasks 解析）、`next_schedule` 用短横线（新通路）——同一份代码不可能产生这种输出。

**根因**：`DeckServer.allow_reuse_address = True`（Windows 上等价 `SO_REUSEADDR`）**允许两个进程绑同一端口**。原有的 `_port_already_served()` 探测存在**启动竞态**：实例 A 还在 import（依赖很重，几十秒），尚未 bind；实例 B 探测得到 `ConnectionRefusedError` → 判定"端口空闲" → 也去 bind → 两个都在监听，连接只落到其中一个。

**修复**：bind 之前先抢**进程级独占文件锁**（`msvcrt.locking` / `fcntl.flock`），把"启动"这段串行化。

**验证**：
```
$ python deck/deck_server.py --port 8787     # 服务已在跑
✗ 端口 8787 已有另一个 deck 实例持有单实例锁，本次拒绝启动。
  双开会造成「新进程空跑、旧进程继续服务」：改代码不生效、请求行为随机。
退出码=3
```

> 踩坑记录：Windows 的字节范围锁是**强制锁**，另一进程持锁后连 `open(...,"a+")` 都会 `Permission denied`。第一版把这种情况当"锁文件打不开 → fail-open 放行"，等于没有锁；必须把 `PermissionError` 判为"已有实例持锁 → 拒绝启动"。

### B11 单实例锁用 pid 文件，删了就等于没有锁

**根因**：`single_instance()` 用 `O_CREAT|O_EXCL` 建 pid 文件。两个缺陷：
1. pid 文件被删（人工清理、残留清理脚本）→ 两个实例都认为自己是唯一 → **双守护**；
2. pid 复用 → 存活判定误判。

本次排查中我执行 `rm logs/watchdog.pid` 就复现了双守护——两个 watchdog 各自 spawn 一个 deck_server。

**修复**：改为内核级独占锁（`logs/watchdog.lock`），锁由进程退出自动释放，不依赖 pid 是否正确。**约定：该锁文件永不手动删除**（锁在 inode 上，删文件等于作废锁）；pid 文件降级为可读信息。

**验证**：
```
$ python scripts/watchdog.py --port 8787      # 守护已在跑
[16:26:15] 已有存活守护进程（锁文件被占用 → Permission denied），本实例退出
```

## 七、防复发

1. **调度层自检**：`python data/task_registry.py` 一条命令看全部任务真实状态，退出码 0=全绿。建议纳入每次改动后的自检。
2. **三态原则**：所有"查询外部状态"的地方，查不到就说查不到（`None`/`Unknown`），**不允许**用 `True` 兜底。本次 3 个虚假绿灯全部源于此。
3. **计划任务统一入口**：新增任务一律走 `scripts/run_task.py`，不要直接指向子目录脚本（`sys.path[0]` 陷阱）。
4. **锁文件永不手动删除**：`logs/watchdog.lock`、`logs/deck_server_<port>.lock`。清理进程用 `psutil`/任务管理器，不要 `rm` 锁文件。
5. **测试即文档守卫**：`test_doc_claims` 会拦住"数据变了、文档没改"。改数据后跑测试，别改测试值了事——先确认数字确实应该变。
