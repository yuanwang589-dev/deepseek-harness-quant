## 二、任务卡

### T1.1 ATR 止损接线

**关联功能**：`risk/position_stop_check.py` 持仓自动止损引擎 → 每日收盘后扫描，输出 `logs/stop_signals_*.json`，直接决定"T+1 是否卖出"。

**为什么改（证据）**：
- `type_stop_rules.py` 为 `reversal` 类型定义了 `atr_stop_mult: 3.0`（"ATR 3× 宽止损替代固定%"，研究员 M2 矩阵）
- 但 `check_position()` 从未读取该字段；`_atr()` 定义了却从未被调用
- `test_gaps.test_atr_stop_implemented` 红：`code.count("_atr(")` 仅 1（定义本身）
- 后果：反转类持仓**实际无止损**，`atr_stop_mult` 是配置空壳

**改什么**：
1. `check_position()` 内，当 `plan.get("atr_stop_mult")` 且 `entry_price` 有效时：
   - 计算 `atr = _atr(bars)`，止损线 = `entry_price - mult × atr`
   - 收盘价 ≤ 止损线 → 输出 `{"rule": "ATR止损", "level": "SELL", "priority": 2}`
   - ATR 不可算（数据不足 15 根）→ 输出 `WARN` 信号"ATR 无法计算"，不静默跳过
2. 结果 `plan` 回显中保留 `atr_stop_mult` 与 `atr_value` 便于复盘

**怎么验（A1）**：
```bash
cd DSHQuant
..\.venv\Scripts\python.exe -m unittest tests.test_gaps.TestLogicGaps.test_atr_stop_implemented -v
# 期望: ok（_atr( 出现次数 > 1）
..\.venv\Scripts\python.exe risk/position_stop_check.py --demo
# 期望: 3 只模拟持仓正常输出；茅台（revalue）不应因 ATR 误触发
```
**反作弊**：不许为了凑计数而写 `_atr(bars)  # noqa` 占位——必须真实参与判断，验收时用 demo 构造一只"跌破 ATR 线"的持仓验证能出 SELL。

### T3.1 WAL 模式全库开启

**关联功能**：所有写入（bulk_loader / incremental_daily / fetcher_*）与所有读取（看板 36 接口）的并发行为。

**为什么改**：
- `fix_st_flags.py:119` 注释自证："避免长连接复用导致 database is locked（2026-08-07 事故）"
- SQLite 默认 rollback journal 下读写互斥；WAL 下读不阻塞写、写不阻塞读
- 这是部署记录坑 1（下载期开看板报 malformed）的**前提条件**之一

**改什么**：
1. 脚本 `data/enable_wal.py`：遍历 `data/cache/*.db`，`PRAGMA journal_mode=WAL` + `PRAGMA busy_timeout=15000`，逐库打印前后模式
2. `io_utils.sqlite_rw()` 连接后自动设 WAL（新库也享受）
3. **不动** 只读连接逻辑（T3.2 单独处理）

**怎么验（C1–C2）**：
- C1：对每个库 `PRAGMA journal_mode` 返回 `wal`（脚本输出全表）
- C2：并发实测——写进程插入 2 万行期间，另一进程连续读 30 次，0 次 locked/malformed
**反作弊**：必须给并发测试的**原始输出**（写进程 PID、读成功次数、错误计数）；只贴 `journal_mode=wal` 不算完成。

### T3.2 只读连接智能降级

**关联功能**：`deck/live_api.py` 全部 36 个接口 + `system_live.py` 探测 + 所有走 `data.cache.db_uri()` 的读取方。

**为什么改（证据）**：
- `data/cache.py:db_uri()` 恒返回 `?mode=ro&immutable=1`
- `immutable=1` 向 SQLite 承诺"文件永不变化"；写入进程改页后，读视图错乱 → `database disk image is malformed`
- 部署记录坑 1 原文："这不是数据损坏，`PRAGMA integrity_check` 返回 ok，停掉看板即恢复"

**改什么**：`db_uri(p, immutable=None)`：
- `immutable=None` 时自动判定：库文件 mtime 距今 < 300 秒，或存在非空 `-wal` / `-journal` 边车文件 → **不加** `immutable=1`（普通只读，安全）
- 否则（库确实静止）→ 保留 `immutable=1`（快路径）
- 显式传 `immutable=True/False` 可覆盖；`stale_secs` 可调
- 新增 `data/write_lock.py`（可选）：写进程开始时 touch `data/cache/.writing`，结束时删除；`db_uri` 检测到该文件同样降级

**怎么验（C3–C4）**：
- C3：库刚被写入（mtime=now）→ `db_uri()` 不含 `immutable=1`；`touch` 后 5 分钟以上的库 → 含 `immutable=1`
- C4：真实场景复现——启动一个写入循环（向 `bars_incr.db` 写 2 万行），同时连续请求看板接口 50 次，0 次 malformed（对比：改动前同样场景必现）
**反作弊**：C4 必须给"改动前会炸、改动后不炸"的对照，只证明改动后不炸不算。

### T3.3 finance.db 补 PIT 披露日

**关联功能**：基本面因子、Beneish 造假检测、回测选股（`bt_runner` 已有 ann_date 口径，但 `finance.db` 无此列）、风险地图。

**为什么改（证据）**：
- `finance.db.finance_report` 31.9 万行，**无任何披露日期列** → 只能用固定延迟近似（部署记录"已知边界"）
- `finance_ts.db.financials_ts` 27.5 万行**有 `ann_date`**，且回测已在用（"按 ann_date ≤ 月末，防前视"）
- 两库口径不一致，正是 `unified.db.dual_source` 表要解决的问题
- **实测可回填**：按 `substr(financials_ts.code,1,6)=finance_report.code AND end_date=period` 关联，可覆盖 **81.3%**（259,454 / 319,038）
- 附带发现：`finance_report.code` 是 6 位（`000001`），`financials_ts.code` 带后缀（`000001.SZ`）——**同一实体两种主键口径**，属数据治理缺陷

**改什么**：
1. 备份 `finance.db` → `backups/finance_before_ann_date_20261018.db`
2. `ALTER TABLE finance_report ADD COLUMN ann_date TEXT`
3. 按上述关联回填（只填匹配行）
4. 新增 `data/backfill_ann_date.py`（可重跑、幂等、打印覆盖率）
5. 在 `docs/资产盘点.md` 记录：ann_date 覆盖率 81.3%、剩余 18.7% 为 finance_ts 未覆盖期、两库代码口径差异

**怎么验（C5–C7）**：
- C5：`SELECT COUNT(*) FROM finance_report WHERE ann_date IS NOT NULL` ≥ 250,000；覆盖率打印
- C6：PIT 抽样——对 `600519` 取 `ann_date` 最新 3 条，人工核对与公告日一致（贴 SQL 结果）
- C7：`PRAGMA integrity_check` = ok；总行数仍为 319,038
**反作弊**：不许用 `period + 固定天数` 伪造 ann_date；必须是真实关联值，抽样可回溯到 `financials_ts` 同一行。
