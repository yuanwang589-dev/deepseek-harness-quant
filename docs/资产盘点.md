### 3.2 Beneish M-Score —— v3.0 数字已证伪，此为实测值

**v3.0 原文**：

> "Beneish M-Score，财务造假排雷，**8 指标全量**（5501 只：HIGH 260 / WATCH 350 / LOW 4891）"

**实测（2026-10-15）**：

```
python risk/beneish.py --scan
→ Beneish 批量扫描: {'total': 3908, 'HIGH': 31, 'WATCH': 7, 'LOW': 3870}
```

**为什么对不上**：`risk/beneish.py` 的模块 docstring 自己就写明是**降级版**——

- 完整 8 指标需资产负债表明细（应收/存货/折旧/总资产/SG&A）→ **数据未入库**
- 降级版只用可算的 4 项近似：`GMI`（毛利率两期比）、`SGI`（单季收入同比）、
  `LVGI`（负债率两期比）、`TATA`（`cfo_to_np` 代理）
- **`DSRI` / `AQI` / `DEPI` / `SGAI` 四项置 0（中性）**，输出 `mode='degraded'`
- 完整版 `risk/beneish_full.py` 的数据源（Tushare 三表 parquet）**0 个文件**，跑不起来

**所以正确表述是**：Beneish 排雷**在跑，但是 4/8 指标的降级版**，实测样本 **3908 只**，与 v3.0 写的只数不符。
降级版会漏判依赖应收/存货/折旧结构的造假——**这是已知能力缺口，不是已解决的防线**。

**核实命令：**
```bash
python risk/beneish.py --scan                     # 真实分布
python risk/beneish_full.py --status              # 完整版数据源：0 个 parquet
grep -n "degraded\|置 0\|数据未入库" risk/beneish.py | head
```

### 3.3 类型定制止损（stop_matrix）

| 类型 | 止损方案 | 实证依据 | 状态 |
|---|---|---|---|
| breakout 突破 | 10% 硬止损 | 硬止损是正资产：夏普 0.81→1.39，回撤 -29%→-8% | ✅ 已实现 |
| reversal 反转 | 删硬止损，改 **ATR 3×** + 时间止损 | 硬止损猎杀率 40%（假止损） | ❌ **ATR 未生效** |
| pv_consensus 量价共识 | 无硬止损，逻辑止损（共识瓦解） | 硬止损摧毁策略：夏普 0.40→-1.38 | ⚠️ 逻辑止损依赖缺失库 |
| quality_gap 质量折价 | 无硬止损，逻辑止损（质量破位） | 硬止损摧毁：夏普 0.65→-0.89 | ⚠️ 同上 |

> **ATR 止损是空壳（实测）**：`risk/position_stop_check.py` 里 `_atr()` **定义后从未被调用**，
> `atr_stop_mult` 配置没有任何代码读取。测试用例 `test_atr_stop_implemented` 当前为**红**。
> 也就是说 **reversal 类型目前没有止损保护**，这一条 v3.0 声称"改 ATR 3×"是不成立的。

> **逻辑止损目前判不了**：`stop_signals` 输出里该条恒为 `level=CHECK` +
> `action="人工复核（TODO：接 finance_ts.db）"`——依赖的库不存在，等于占位符。

**核实命令：**
```bash
grep -n "_atr" risk/position_stop_check.py          # 定义处 vs 调用处
python -m unittest tests.test_gaps.TestLogicGaps.test_atr_stop_implemented -v
```

> **纪律 ≠ 普适安全垫**。防守型策略的硬止损是收益杀手，真正安全垫是
> "无硬止损 + 逻辑失效止损 + 基本面排雷"——但**后两项当前都因数据缺失而打折**。

所以 `active` 这个状态在当前数据条件下**不代表"可立即使用"**，只代表

**★三个必须说清的口径**：

1. **`STRONG_TABLE` 那 27 个的分是"派生"不是"实测"**。本仓没有它们的计算通路
   （源目录 `data/factorpool/output/daily_scores/` 不存在），跑不了评估器。
   `seed_pool.derive_score()` 用**固定权重**把 F1 已实测的
   `icir120(0.40) / win_rate(0.25) / t120(0.20) / n_days(0.15)` 折成 0-100 分，
   与 `eval_ts`/`factor_evaluator` 同量纲；**原始四项指标全量存进 `last_eval_detail`**，
   可自行复算校验。守卫用例 `test_strong_table_scores_match_formula` 会复算比对。

2. **`EXPRESS_BANNED` 的两个因子被强制压成 `candidate`**：`lhb_jg_cnt_20` 与 `limup_ex_5`
   的截面 ICIR 是全库前三（派生分 100），但组合层实证是**负超额**
   （-5.63pp / 6-7 个负年），已被移出直通白名单。按分数自动流转会把它们标成
   `active`（=可接入策略）——**那是错的**。用例 `test_express_banned_never_active` 守着。

3. **`new_high_250` 标 `retired`**：它的 `direction=0`（各口径 IC 均负，已剔除），
   入池时按"已剔除"归档而非留在候选里。

**顺带修掉的两个真 bug**（都在评估通路上，属"质量"的一部分）：

- **`lifecycle.evaluate_factor` 的评分解析从未生效**：它用 `line.split(":")[-1]` 解析
  `factor_evaluator` 的输出，而真实输出行 `  评分 54.0 ｜ 反向弱有效 ｜ ...` **没有冒号** →
  `float()` 必抛 `ValueError` → `score` 恒为 `None` → 下游
  `"active" if score and ... else "retired"` 把**每一个 cross_sectional 因子都判成 retired**。
  即"评估通路从来没 work 过，而且每次评估都在淘汰因子"。已改为正则解析，
  并加"拿不到分时**不流转状态**"的保护。
- **`registry.py` 连接泄漏**：11 个方法都写 `with sqlite3.connect(...) as con:`，
  但那是**事务**上下文管理器，退出只 commit/rollback、**不关连接** → 句柄泄漏，
  Windows 上库文件被占用无法删除。已改为退出即关闭的 `_conn()`。
  同时 `register()` 补上 `note` 的更新（原来对已存在因子只更新
  family/kind/source/freq/direction，描述改动永远写不进去）。

## 10. 为什么区别于其他 AI 炒股系统

| | 其他 AI 炒股系统 | DeepSeek HARNESS Quant |
|---|---|---|
| AI 角色 | 直接荐股 / 预测股价（黑箱） | 只驱动：控制 / 挖因子 / 审计 / 蒸馏（不预测） |
| 决策来源 | 模型输出（不可复现） | 写死引擎的确定性计算（可复现） |
| 验证 | 无（信模型） | T+1 + 分年度 + 覆盖率核查（信数据）——⚠️ **"九步验证"当前为方法论，见 §5.1** |
| 红线 | — | AI 不预测个股 |

> **语言模型是大脑，量化引擎是手，数据系统是事实。**

**这个定位本身是成立的、也是本项目真正的差异点。** 但要让它可信，
前提是 §9 的缺口被补上——因为"信数据"的系统，**最不能容忍的就是数据层是空的**。
